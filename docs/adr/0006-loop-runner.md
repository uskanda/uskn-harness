# ADR-0006: 仕様PRのループはハーネスに置き、段階2ではサーバー単位で動かす

- 状態：採用（2026-10-01）
- 決定者：uskanda（change `add-loop-run` のgrilling。第1ラウンドのQ2とQ10、第3ラウンドのQ1とQ2）
- 関連：調査と提案は `docs/loop-engineering-2026-09.md`、仕様PRは `spec-pr` スキル（change `add-spec-pr`）

## 文脈

仕様PRを作業指示として受け取り、実装役と監査役を完了基準か停止条件に達するまで交互に動かすループを試験的に導入する。
対象のプロダクトリポジトリはGitHubとGitLabにまたがる。
ADR-0001の原則により、プロダクトリポジトリには規約が求めるファイルだけを置き、ほかはインストーラが配る。
ハーネスのhook（write-guard、bash-guard、verify gate）は、Claude Codeのセッションに読み込まれて働く。

## 決定

1. ループ本体はハーネスに置く。入口は `bin/uskn-loop`、補助ファイルは `loop/` とし、`uskn-harness sync` が `~/.local/bin/uskn-loop` を張る
2. プロダクトリポジトリには、ループのためのファイルを何も足さない。workflowのファイル、秘密情報、ラベルを置かない
3. 段階1では、ユーザーが手元のクローンから `uskn-loop run <PR/MR>` で手動で起動する。作業は手元のworktreeで行う
4. 段階2では、常時動くマシン1台に、PRとMRを定期的に見てジョブを起動するウォッチャーを1つ置く。リポジトリごとには置かない
5. 実装役と監査役は、ラウンドごとに別の `claude -p` として起動する。続けるか止めるかは、LLMでなくスクリプトの決まった規則で判定する
6. ホストへの操作（`gh` と `glab`）は `loop/lib/host.sh` の1か所にまとめ、GitHubとGitLabの両方に対応する

## 検討した代替案

| 案 | 退けた理由 |
|---|---|
| リポジトリごとのCI（GitHub Actions、GitLab CI） | workflowのファイルと秘密情報がリポジトリの数だけ増え、プロダクトリポジトリに置くものが増える。ハーネスのhookもCIのランナーでは働かない |
| Claude Codeのroutines | GitHubだけで、起動できる出来事はPRとReleaseに限られ、コメントでは起動しない。研究プレビューでもある |
| 1セッション内のsubagentを監査役にする | 文脈が積み上がり、続けるかどうかの判断がLLMに残る。停止条件を確実に守れない |
| `/goal` で続ける | 評価モデルは会話の記録しか読まず、コマンドもファイルも見ないので、独立した監査役にならない |

## 結果

- 良い点：GitHubとGitLabを同じ実装で扱える。ハーネスのhookとスキルが、ループの中の実装役にもそのまま働く。プロダクトリポジトリは軽いままである
- 引き受けるコスト：段階2では、常時動くマシンとその上の資格情報をユーザーが管理する。段階1は手元のマシンで動き、コンテナの隔離が無い
- 後回し：ウォッチャー、ラベル、1日ごとの費用上限、常駐させるマシン、認証の方式は段階2で決める。コメント駆動とIssueは段階3で決める
