## Context

動機はproposal.mdのWhyを参照。
既存のセンサーはtextlintとprhで、これらは文の質と表記のゆれを見る。名前が実在するかどうかと、語が既知かどうかは見ない。
実測では、地の文のバッククォートの名前192個のうち24個が実在しなかった。内訳は外部の名前とプレースホルダーが大半で、実害のある古い名前が数個。
カタカナ語は異なり132語で、1回だけ現れる45語もすべて一般語だった。今の文書は比較的きれいで、予防として入れる段階にある。

## Goals / Non-Goals

- Goals: 名前の出所を規約にし、機械で確かめる。用語集の置き場をリポジトリ間で揃える。既存リポジトリを一括で直す道具を持つ
- Non-Goals: 会話から用語を自動抽出する仕組み。記録（archiveと調査文書）への適用。プロダクトリポジトリへの用語集の配布

## Decisions

1. 用語集は `openspec/glossary.yml`。どのリポジトリでも同じ相対パスにする。導入済みリポジトリなら `openspec/` は必ずあり、仕様と語彙が同じ場所に集まる。ハーネス自身も同じ場所に置いてドッグフーディングする
2. 別名の指摘は `terms-check` が用語集を直接読んで行う。prh.ymlの生成はしない。生成の段取りを増やさないため。編集するファイルはリポジトリごとに1つで足りる。汎用の表記ゆれ（ユーザー、サーバー）はprh.ymlが引き続き見る
3. `terms-check.sh` は2つのモードを持つ。標準入力にJSONが来たらhookとして `additionalContext` を返し、パスを引数に取ったらCLIとして指摘を出して非ゼロで終わる。`journal-update.sh` と同じ形
4. 名前の実在は、gitが追跡するパス、その要素、追跡ファイルの中身、用語集の語、許可リストで判定する。除外は山かっこを含む語、代入の形、版の例。この4つの除外規則で、実測24件のうち許可リストが要るのは10件程度まで減る
5. 未知語の一般語リストは `skills/ja-writing/common-words.txt`。本リポジトリの132語を種にする。プロダクトリポジトリへは配らず、各リポジトリが自分のリストを持つか、用語集だけで運用する
6. `audit-writing` は洗い出しから始める。検証の指摘を潰すだけでは、用語集の無いリポジトリで何も直らないため。用語集づくりは対話にし、定義の推測を禁じる

## Risks / Trade-offs

- ［未知語の検査がうるさい］→ 一般語リストを132語で始め、指摘が出た語を足す。hookは警告だけで止めない
- ［用語集が育たない］→ `audit-writing` が対話で作る道を用意する。空の用語集でも名前の実在検査は動く
- ［`openspec/` を持たないリポジトリ］→ 用語集に依る検査を飛ばし、名前の実在検査だけを行う
- ［形態素解析を使わないので語の切り出しが粗い］→ カタカナの連続とかぎかっこという単純な規則にし、取りこぼしを許す。造語の多くはこの2つの形で現れる

## Migration Plan

センサーを入れる前に、本リポジトリの用語集と一般語リストを埋める。
実測で見つかった実在しない名前を先に直し、`make verify` が通る状態にしてから `verify-terms` をverifyに繋ぐ。
