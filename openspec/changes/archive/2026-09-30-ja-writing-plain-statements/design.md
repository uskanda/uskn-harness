# Design

## Context

動機は `proposal.md` のWhyを参照。決定の経緯は `grilling.md` にある。

- `skills/ja-writing/textlintrc.json` は3つのプリセットと `prh` を有効にしている。hook `textlint-check` と `make verify` の `verify-textlint` は、どちらもこの設定でtextlintを実行する
- textlintの追加パッケージは、`deps.json` のtextlintの `bundle` に並べる。`uskn-harness sync --tools` と `doctor` は、`bundle` の各パッケージの版も照合する。足りなければ `sync` が `npm install -g` を実行する
- `make verify` のtextlintの対象は `DOCS_JA`（README、`docs/setup-new-machine.md`、ADR、main spec、進行中のchange）。`docs/proposal-2026-09.md` とarchiveは記録として対象外
- `skills/ja-writing/SKILL.md` は英語で103行。日本語の例はスキルの中に書いても、かなの割合が6パーセントに届かないのでhookは検査しない
- 設定に書いたルールのパッケージが1つでも無いと、textlintはどのルールも読まず、`No rules found` を出して終了コード1になる。hookはこれを「lintできなかった。`uskn-harness doctor` を実行する」と返す

## Goals / Non-Goals

**Goals:**

- 比喩の動詞を、今のhookと `make verify` の経路のまま、errorとして検出する
- 検出の範囲（検出する文と検出しない文）をbatsで固定する
- 計算で検出できない癖（否定文と肯定文の組、強調の読点、対句）を、スキルの読み直しの手順とaudit-writingで扱う

**Non-Goals:**

- 独自の `.textlintrc` を持つプロダクトリポジトリへの展開
- en-writingの変更
- archiveと `docs/proposal-2026-09.md` の書き直し

## Decisions

### 1. 検出は `@textlint-rule/textlint-rule-pattern` で行う

textlintの公式organizationのルールで、MITライセンス。正規表現の一覧を設定に書き、1件ごとに独自のメッセージを返せる。
本文（Str）だけを見て、コード（1個と3個のバッククォートで囲んだもの）は既定で検査しない。`allowNodeTypes` で引用ブロックも外せる。

比べた案は2つ。
`prh.yml` は置き換え辞書で、正しい表記を1つに決められない比喩には合わない。`--fix` が誤った置き換えをする。
`terms-check.sh` の拡張は、用語の検査と文体の検査が1つのスクリプトに混ざり、hookの出力も分かれる。

### 2. 正規表現の一覧

語ごとに1つのパターンを書く。活用は語幹の後ろの1字で受ける。複合語の一部として現れる字は否定の先読みと後読みで外す。

| 語 | パターン | 外すもの |
|---|---|---|
| `倒す`・`倒れる` | `に倒[さしすせそれ]` | なし（`圧倒`、`面倒` は「に」が前に来ない） |
| `寄せる` | `(?<![左右上下央])に寄せ` | `左に寄せる` などの文字どおりの用法 |
| `効く` | `(?<![有無実])効[かきくけこい]` | `有効か`、`無効か`、`実効` |
| `壊れる`・`壊す` | `(?<!破)壊[れさしすせそ]` | `破壊した` |
| `添える` | `添え(?!字)` | `添え字` |
| `刺さる` | `刺さ` | なし |
| `響く` | `(?<!影)響[かきくけこい]` | `影響か` |
| `担保` | `担保` | なし |
| `回す` | `を回[さしすせそ]` | `後回し`（「を」が直前に来ない） |
| `拾う` | `拾[わいうえおっ]` | なし |
| `落とす` | `(?<!見)落と[さしすせそ]` | `見落とす` |
| `握る` | `握[らりるれろっ]` | なし |

この一覧で測った件数は、現役の文書（`DOCS_JA`）で22件、記録で91件。現役の22件はすべて比喩の用法だった。

メッセージは日本語で、語と直し方と参照先を1行で示す。形は `比喩の動詞「効く」。何をどう扱うのかと、その対象を書く（ja-writing）` とする。
指摘の強さは既定のerrorのまま。

### 3. スキルの構成

`skills/ja-writing/SKILL.md` の構成は次のとおり。英語で書き、日本語は例文だけにする。

- `## Sentences` に3規則を足す（主文を先に、比喩の動詞を使わない、印象を狙った形を使わない）
- `## Sentences` の既存の分割の行に、分けてよい条件を足す
- `## Register` の表から「体言止め可」を外し、体言止めの範囲を1行で書く
- 新しい節 `## Rereading` を置き、残る文章を書き終えたときの読み直しの問いを1つ示す。例文には資料の例3を使う
- 新しい節 `## When prose is called machine-written` を置き、指摘を受けたときと指摘するときの手順を示す
- `## Fixing findings` の表に比喩の動詞の行を足す
- `## Worked example` に2つ目の例を足す。直す前は `拒否の側に倒す`、直した後は `判定できないときは拒否する`
- 冒頭のセンサーの説明を「3つのプリセットと辞書」から、パターンのルールを含む形に直す

`skills/audit-writing/SKILL.md` は4段階の構成を保つ。
洗い出しでは、textlintの出力に比喩の動詞が含まれる。文を読み、主文の置き方と印象を狙った形の候補を足す。
用語集づくりの段階で、挙げた文の意味を10個ずつ問う。修正の段階では、意味を確かめた文だけを書き直す。

### 4. batsの配置と例文

`<bin/tests/ja-writing-rules.bats>` を足す。例文は `<bin/tests/fixtures/ja-writing/>` に置く。

- `<detect.txt>`：検出されるべき文を1行に1文ずつ置く。資料の例1・2・4・5と、archiveの実例を入れる。`.txt` にするのは、書き込んだときにhookが指摘を返さないようにするためである。先頭の `#` の行に資料のURLを書く
- `<pass.md>`：検出されてはならない文。文字どおりの用法、複合語、バッククォートの中の悪い例、引用ブロックの中の悪い例を入れる。ほかのルールの指摘も出ない文にする
- テストは実際のtextlintをハーネスの設定で実行する。`<detect.txt>` では、`#` 以外の各行にパターンのルールの指摘が1件以上あることを確かめる。`<pass.md>` では指摘が0件であることを確かめる
- textlintかルールのパッケージが無いときは `skip` にし、`VERIFY_STRICT=1` のときは失敗にする。このテストはCIの `VERIFY_STRICT` をそのまま受け取り、それで欠けた道具を失敗にするかを決める。そのため `terms-check.bats` とは違い、setupで消さない

### 5. 現役の文書の書き直し

`writing-guidelines` のtasksの4.2と同じく、main specを直接直す。直すのは文言だけで、要件の意味は変えない。

| 元の語 | 書き直しの方向 |
|---|---|
| `効く`（設定や許可について） | 適用される、有効になる |
| `効く`（修正について） | 問題が直る |
| `壊れた入力`（Scenarioの見出し） | JSONとして読めない入力 |
| `壊す`（ファイルについて） | 変更する、上書きする |
| `添える` | 含める、書き加える |
| `担保` | 保証する、確かめる |
| `を回す` | 進める、実行する |

`docs/adr/0001-harness-architecture.md` の日本語のセンサーの行には、パターンのルールを書き足す。

## Risks / Trade-offs

- ルールのパッケージが入る前に設定が届くと、そのマシンでは日本語の検査がすべて止まる → スキルはsymlinkで配るので、設定は `git pull` の時点で届く。hookは `doctor` の実行を促し、`sync --tools` で直る。CIは `sync --tools` の後に `make verify` を実行する
- `ファイルが壊れる` のような文字どおりの用法も検出する → ユーザーの判断として受け入れる。比喩でない動詞に言い換えるのは難しくない。例を示すときはバッククォートか引用ブロックに入れる
- ひらがなで書いた `きく` は検出しない → ひらがな書きは対象にしない。漏れは読み直しの手順で扱う
- 読み直しの手順は推論センサーで、実行されたかを機械では確かめられない → 計算で検出できる部分はtextlintに置いた。残りは規則として明示し、指摘されたときの手順で補う

## Migration Plan

1. mainへ統合したあと、各マシンで `uskn-harness sync --tools` を実行する。`doctor` の警告が消えれば完了
2. 戻すときは、`textlintrc.json` からパターンのルールの項目を外す。`bundle` の行は残しても害はない
