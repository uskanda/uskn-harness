# grilling 記録: ja-writing-plain-statements

発端は資料「AI臭い文章とは何なのか」（Kiminori Yokoi、2026-09-28、<https://speakerdeck.com/nasuvitz/ai-kusai-bunshou-toha-nanina-no-ka>）。
資料の悪い例5つを今のtextlintの設定にかけると、指摘は0件だった。
archiveの設計文書には、資料の例2と同じ型の文（`拒否の側に倒す`）が4件あった。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| 変更の範囲 | 直前の提案1〜4をすべて入れる。1はja-writingの `## Sentences` への3規則とworked example。2は既存の規則との食い違いの解消。3は計算センサーと推論センサー。4は指摘の受け方 | 会話中に確認 |
| 検出の仕組み | `@textlint-rule/textlint-rule-pattern` 2.0.2を `textlintrc.json` に足し、`deps.json` のtextlintの `bundle` にピンする。hookと `make verify` は今の経路のまま使う | 第1ラウンド Q1 |
| 検出する語の範囲 | 方向の比喩に加え、抽象的な動詞も検出する。ユーザーの判断は「これらの動詞が使われるときは、おおよそ適切な使い方ではない」 | 第1ラウンド Q2（ユーザーの指示で推奨案から変更） |
| 検出する語の一覧 | `側に倒す`・`倒れる`、`寄せる`（直前が左・右・上・下・中央のものは除く）、`効く`、`壊れる`・`壊す`、`添える`、`刺さる`、`響く`、`担保`、`回す`、`拾う`、`落とす`、`握る`。`閉じる` は文字どおりの用法が多いので入れない | 第2ラウンド Q10 |
| 指摘の強さ | errorにして `make verify` を失敗させる。誤検知は `allows` で除く | 第1ラウンド Q3 |
| batsの例文 | 検出されるべき文として、資料の例1・2・4・5とarchiveの実例を入れる。検出されてはならない文として、`左に寄せる` のような文字どおりの用法を入れる。資料の例3（短い否定文と短い肯定文の組）は計算では検出できないので、読み直しの手順の例文にする。冒頭に資料のURLを書く | 第1ラウンド Q4、第2ラウンド Q10 |
| 体言止めを許す場所 | 表のセル、箇条書き、見出し、コミットの要約行に限る。本文の文では使わない。`archive-push` の要約行の形は変えない | 第1ラウンド Q5 |
| 読み直しの対象 | 3規則はチャットを含むすべての日本語の文章に適用する。「文だけで誰が・何を・どうするかを言えるか」の読み直しは、ファイル、コミットメッセージ、PR本文のように残る文章だけで行う | 第1ラウンド Q6 |
| audit-writingでの扱い | 洗い出しで該当する文を挙げ、ユーザーに意味を確かめてから書き直す。意味を確かめられない文は未解決として残す | 第1ラウンド Q7 |
| 指摘の受け方の範囲 | 指摘されたときも、ほかの人の文章に指摘する側に回ったときも、該当する文と規則を挙げる。「AI臭い」の一言で済ませず、意味を問う。対象はja-writingだけで、en-writingは変えない | 第1ラウンド Q8 |
| 現役の文書にある該当箇所 | 前例（`writing-guidelines` のtasksの4.2）に倣い、README、ADR、main specの約20件を文言だけ直接直す。要件の意味は変えない。Scenarioの見出しも対象にする | 第2ラウンド Q11 |
| 悪い例の書き方 | 仕様やスキルで悪い例を示すときは、バッククォートか引用ブロックに入れる。ルールには `allowNodeTypes: ["BlockQuote"]` を指定し、`textlint-disable` は使わない | 第2ラウンドで提示し、会話中に確認 |
| 文を分ける規則 | 100字の上限は残す。分けると主語・対象・条件が抜けるなら分けず、「〜ため、」などでつなぐ | 会話中に確認 |
