# grilling 記録: add-loop-run

このgrillingは `add-spec-pr` と共通で行った（調査と提案は `docs/loop-engineering-2026-09.md`）。
この表には `add-loop-run` に関わる行だけを載せる。残りの行は `add-spec-pr` のgrilling.mdにある。

## 決定

| 決定 | 選択 | 出典 |
|---|---|---|
| changeの分け方 | 2つに分け、`add-spec-pr`、`add-loop-run` の順に進める。grillingは1回で両方を扱い、同じ対話を2つのgrilling.mdに分けて記録する | 第1ラウンド Q1 |
| ループ本体の形と起動 | 独立したコマンド `uskn-loop` をリポジトリの `bin/` に置き、`uskn-harness sync` が `~/.local/bin` にリンクする。ターミナルから `uskn-loop run <PR>` で起動し、段階2で `uskn-loop watch` を足す。インストーラの下位コマンドにもスキルにもしない | 第1ラウンド Q2 |
| 実装言語 | bashとjq。batsで `claude`、`gh`、`glab` を偽物に差し替えてテストする。段階2で常駐やキューの処理が重くなったら見直す | 第1ラウンド Q3 |
| 実装役の権限 | `--permission-mode auto` と `--permission-prompts none`。`-p` でもautoの分類器が操作を承認し、承認されない操作は拒否されることを公式文書で確かめた | 第1ラウンド Q5 |
| 監査役のモデルと道具 | 実装役と同じOpus 5.5で、effortはhigh。道具は読み取りとBashに限り、EditとWriteは与えない。監査で作業ツリーが変わったら、ループ本体が元に戻す | 第1ラウンド Q6 |
| pushの時点 | ラウンドごとにpushする。完了したらdraftを解除してレビュー待ちにする | 第1ラウンド Q7 |
| archiveの時点 | 人がPRを確認したあと、PRのブランチで `/archive-push` を実行する。archiveのコミットがPRに入ってからマージする | 第1ラウンド Q8 |
| 試験の対象 | このハーネスで1件、プロダクトリポジトリ（monolith、uskn75-kb）で2件 | 第1ラウンド Q9 |
| ADR | このchangeの中でADR-0007を書く。ループをハーネスに置くこと、プロダクトリポジトリに何も足さないこと、段階2ではサーバー単位のウォッチャーにすることを記録する | 第1ラウンド Q10 |
| 受け付けるPR | 今いるリポジトリのoriginにあるopenのPRで、headブランチがforkでなく、作成者が `gh` のユーザーで、archiveされていないchangeがちょうど1つあり成果物がそろっているもの。GitLabのMRにも同じ4条件を課す | 第2ラウンド Q4（ユーザーがGitLabの考慮を追加） |
| 作業場所 | 手元のクローンに `.claude/worktrees/loop-pr-<番号>` のworktreeを作る。ラウンドをまたいで使い回し、完了したら消す | 第2ラウンド Q5 |
| 状態の記録と再開 | `~/.local/state/uskn-harness/loop/<owner>/<repo>/<番号>/` に、ラウンドごとの判定JSON、費用の見積もり、ログを置く。同じPRの二重実行はロックファイルで防ぐ。中断後の再実行はラウンドの数えを引き継ぎ、`--reset` で最初からやり直す | 第2ラウンド Q6 |
| 停止条件の数値 | 5ラウンド。実装役は1回10ドルと60分、監査役は1回3ドルと20分、PRごとの合計は40ドル。連続する2ラウンドで修正必須の指摘と失敗する検査の集合が同じなら止める。pushの拒否と基底ブランチとの衝突でも止める。費用は `total_cost_usd` の見積もり額で、`--max-budget-usd` はこの見積もりが上限に達したら実行を止める | 第2ラウンド Q7 |
| 実装役の指示とコミット | 1ラウンド目は `/opsx:apply <change>` を実行させる。2ラウンド目以降は、監査役の修正必須の指摘と、失敗した計算的センサーの出力を渡して直させる。コミットは実装役が `commit` スキルで行い、ループ本体は未コミットの変更が無いことを確かめてからpushする。モデルとeffortはユーザー設定の既定値 | 第2ラウンド Q8 |
| 計算的センサー | 毎ラウンド、検証規約（verify-fastでなく全体）、`openspec validate <change> --strict`、tasks.mdの完了、基底ブランチとの差分の検査を確かめる。テストファイルの削除とskipの印の追加は、tasks.mdが求めていない限り修正必須。検証の設定の変更は監査役に確認させる | 第2ラウンド Q9 |
| 監査役の判定の形 | `--json-schema` で返させ、`structured_output` から読む。全体の判定、シナリオごとの対応、指摘の一覧（修正必須と推奨、ファイルと行、要約、根拠）、人の判断が要るときの問いの4欄 | 第2ラウンド Q10 |
| 進捗コメントの形式 | 日本語で1つのコメントを書き換える。先頭に状態、続けてラウンドごとの表、最新の指摘は折りたたむ。見分け用の印 `<!-- uskn-loop -->` を入れる。実装役と監査役への指示は英語で書く | 第2ラウンド Q11 |
| 完了時と停止時の扱い | 完了したらdraftを解除し、結果のコメントを新しく書く。止めたらdraftのまま、理由と問いをコメントに書く。段階1ではラベルを使わない | 第2ラウンド Q12 |
| GitLabの範囲 | GitHubとGitLabの両方を実装し、ホストへの操作を1か所にまとめる。GitLabは偽物の `glab` を使ったbatsで確かめ、実機での試験は対象のGitLabリポジトリができたときに行う | 第3ラウンド Q1 |
| ループの案内の時期 | 仕様PRの本文でのループの起動方法の案内は、`add-spec-pr` でなくこのchangeで足す。あわせて、スキルが名指しするコマンドの実在を確かめるテストが、リポジトリの `bin/` のコマンドも認めるようにする | 実装中に会話中で確認（2026-09-30） |
| 補助ファイルの置き場 | 最上位に `loop/` を作り、入口は `bin/uskn-loop` にする。AGENTS.mdのLayout表に1行足す | 第3ラウンド Q2 |
