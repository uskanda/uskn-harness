## Context

`session-start.sh` は `AGENTS.md` の `## Branch model` にあるyamlを、awkで1行1キーとして読む。`push` の保護判定は `skills/git/push/SKILL.md` の手順3にあり、スキル本文の指示でエージェントがファイルを読み、APIを呼ぶ。動機はproposal.mdのWhyを参照。

## Goals / Non-Goals

**Goals:**

- 宣言があるリポジトリで、`push` の保護判定にツール呼び出しを1回も使わない
- 宣言が無いリポジトリの動きを変えない

**Non-Goals:**

- ホストの保護設定と宣言のずれを検出すること
- 既存のプロダクトリポジトリへ宣言を書き足すこと

## Decisions

### 宣言はBranch modelの上書きキーに置く

既存の上書きの仕組みと同じ場所、同じ読み方で済み、hookが起動時に1回だけ読む。自由文の明記を `CLAUDE.md` に書く案は、エージェントが毎回ファイルを読むため今の問題そのものである。APIの結果を保存して使い回す案は、ユーザーが選ばなかった。

### 値は1行の `,` 区切り

読み取りは1行1キーのawkで、yamlの配列を読めない。`none` とglobパターンの並びだけにすれば、jqの無い環境でも同じ処理で読める。表記は `protected: main, release/*`。

### `--plain branches` は4行のまま

既存の仕様とテストは4行ちょうどを求め、ブランチ名を使うスキルが読む。保護ブランチの宣言は `<repo-context>` と `--json` に出し、`--plain branches` には足さない。`push` は `<repo-context>` が無いとき `--json` を使う。

### 宣言をAPIより優先する

宣言があれば `push` はAPIで確かめない。宣言が古くても、pushはホストに拒否されるだけで、`push` は `--force` を使わない。拒否の報告に「判定はAGENTS.mdの宣言による」と書けば、ユーザーが宣言を直せる。

## Risks / Trade-offs

- 宣言が `none` なのにホストで保護されている：pushが拒否され、コミットは保護ブランチ上に残る。報告に判定の根拠を示し、ユーザーが宣言を直すか新規ブランチへ移す
- 宣言したパターンの書き間違い：一致せず保護されていないと判定される。上と同じくホストの拒否で止まる
